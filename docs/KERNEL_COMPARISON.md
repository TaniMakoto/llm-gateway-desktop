# 本地网关内核选型评估

日期：2026-09-21。这是源码审阅判断，没有进行三者性能对测或迁移原型。

## 结论

当前建议继续现有产品，聚焦协议正确性、回归测试和继承模块解耦；不建议为了追平参考项目的功能数量而换底座。若近期核心需求转向多种订阅 OAuth、凭证刷新、多账号池和更多原生协议，优先验证「现有桌面 UI + CPA 独立子进程」；不建议深度裁剪 sub2api 作为桌面底座。

这一结论依赖当前可见需求：本地单用户网关，以配置 API URL/Key、别名和跨协议调用为主。OAuth 是否成为第一优先级是改变决策的重要条件，不把继承代码中的 OAuth 模块视为已完成产品接入。

## 哪些差距值得补

| 能力 | 当前项目 | CPA | sub2api | 本地产品取舍 |
|---|---|---|---|---|
| 桌面/便携/托盘 | 已有直接集成 | 服务内核，另有 EasyCLIProxyAPI 桌面项目 | 主要是服务端与 Web 管理台 | 保留现有资产 |
| Chat/Responses/Messages 与 SSE | 已有转换及边界测试；需矩阵验收 | 广泛 translator / executor 实现 | 广泛网关适配实现 | 按实际客户端验证保真 |
| 模型别名与路由 | 每模型协议、别名策略、四种调度 | 别名池、跨 provider 调度、优先级/轮询/加权/亲和 | 账号/分组调度与粘性选择 | 已有基础，不应重做同名能力 |
| 退避、容量与诊断 | 冷却、熔断、并发、排队、测试台、正文录制 | auth/model 冷却、刷新、重试及诊断 | 账号并发、排队、调度缓存与运维体系 | 优先补可靠性验证 |
| 多订阅 OAuth/多账号池 | 有继承模块，当前网关没有完整产品入口 | 是核心能力 | 是核心能力 | 确有需求时 CPA 优势显著 |
| Gemini 原生/WS 等入口 | 当前公开路由没有 | 有相关协议与 WS 实现 | 有相关协议与 WS 实现 | 按需，不为追平而扩张 |
| 用户/余额/套餐/销售计费 | 网关产品不需要 | 不以 SaaS 计费为中心 | 深入领域模型与请求链 | 不移植 |
| 本地依赖 | Rust/Tauri + SQLite | 可采用文件配置和凭证的 Go 服务 | 标准部署含 PostgreSQL/Redis | 桌面减少外部服务 |

源码规模或功能数量不等于可靠性；现有测试也不证明三者在我们的输入上行为等价。

## 继续现有项目的收益与代价

已经完成的产品资产包括每模型协议配置、跨供应商别名聚合、模型能力修正、测试台、诊断录制、系统代理及桌面生命周期。这些换内核后仍需逐项映射，不能只搬 UI。

已经补齐的关键债务：Chat 原生候选不再往返 Responses；跨协议转换按候选独立执行；未知别名在统一网关配置存在时明确拒绝；`GatewayRuntime` 已从 CLI 接管服务中拆出；冷却、熔断、会话亲和和轮询状态的作用域已按 CPA 调度语义对齐。

剩余债务主要在产品边界之外：`lib.rs` 和 `services/mod.rs` 仍包含 MCP、Skills、外部应用配置、同步等继承模块；`handler_context.rs` 仍使用 `AppType` 和应用级代理设置，供应商也仍需在 `claude`/`codex` 域物化。继续精简时应保留既有数据库迁移，并逐批验证依赖可达性。

## 为什么不直接迁移 CPA

CPA 是合理候选，且已有跨供应商路由、模型别名池和可定制 SDK，不应误判为只能管理 OAuth。`sdk/cliproxy/builder.go` 提供生命周期、配置、鉴权管理和扩展入口；`sdk/cliproxy/auth/` 承担调度；`internal/runtime/executor/` 与 `internal/translator/` 分开。

但接口名称一致不等于我们现有行为可以原样迁移：

- 我们按 alias 配置策略和权重，协议属于单个模型条目；CPA 的路由与配置组织围绕 provider/auth/model，需验证策略作用域和优先级。
- `openai_compat_executor.go` 的常规执行走 `/chat/completions`，compact 是单独分支。不能因为 CPA 暴露 Responses 下游，就假设任意第三方 Responses-only 上游都能通过普通 OpenAI-compatible 配置保持原语义；需验证合适的执行器与配置。这不是断言 CPA 所有执行器都不支持 Responses 上游。
- 会话亲和、故障转移顺序、并发容量、reasoning 参数、模型能力覆盖和录制行为都要建立映射，当前 SQLite 数据需要迁移方案。
- Tauri/Rust 不能直接导入 Go SDK。实际选择通常是独立子进程；Go 包装服务可使用 SDK，但要承担进程回收、启动就绪、端口冲突、配置更新、版本匹配与打包工作。FFI 会引入额外复杂性，不作为首选。

如果选择 CPA，优先保持上游内核接近原版，通过配置/管理接口或薄 Go 包装扩展；少改核心调度和 translator。大量删除内核再持续追合并，会抵消复用价值。首个原型应替换一条完整请求路径，避免长期让 Rust 和 CPA 同时负责转换、重试和计数。

## 为什么 sub2api 更不合适

`RUN_MODE=simple` 确实存在，README 表明它隐藏 SaaS 功能、跳过计费，但它不是独立的精简内核：

- `backend/internal/server/middleware/api_key_auth.go` 在 simple 分支之前仍检查关联用户及分组，并向上下文写入 `AuthSubject` 和 group。
- `backend/internal/handler/gateway_handler.go` 持有 `BillingCacheService`，在请求中获取用户并发名额、调用计费资格接口，并把订阅传入 usage 流程；simple 可短路业务判断，但服务依赖仍在。
- `backend/cmd/server/wire_gen.go` 构造 Redis 缓存、用户/订阅/计费/调度等服务；`deploy/docker-compose.yml` 标准方案配置 PostgreSQL 和 Redis。

因此删掉支付页面、用户页面并不能得到独立的本地网关。若要进一步去除这些概念，需改鉴权上下文、handler、领域模型、repository、缓存与依赖注入，并重新验收。它适合拿来研究错误分类、账号冷却、并发调度和流中断处理，整体迁移收益不及 CPA。

## 实施顺序与决策门槛

1. **锁定契约。** 做三下游 × 三上游的 JSON/SSE 矩阵；覆盖工具往返、reasoning、空正文、异常 SSE、断流和取消。测试必须经过真实网关，不能只访问 mock。
2. **修影响日常使用的问题。** 优先测试失败暴露的字段丢失、错误误判、重复终止事件、容量泄漏与故障转移问题；保留 usage、上游配额/429 状态及耗时诊断，它们不等于销售计费。
3. **小步精简。** 从 Tauri 命令和启动根节点梳理依赖，拆网关运行服务，逐批移除不可达外围模块与依赖；每批通过完整 Rust 测试、构建和协议回归。
4. **按需求触发 CPA 原型。** 若确认 OAuth 账号池、刷新及 Gemini/WS 是近期核心功能，以同一套契约测试比较 CPA，覆盖任意 Responses 上游、跨协议别名、路由策略、能力覆盖和便携包生命周期。
5. **通过后才决定替换。** 只有现有必需功能能够保持、新增功能显著受益、主要修改能留在适配层时，才投入配置迁移与内核切换。未做原型前不承诺工期或性能提升。

以上为选型时的结论。后续用户批准执行，首轮实施已完成以下代码变更：真实 HTTP 协议矩阵、Chat SSE 字符分片与错误终态修复、独立 `GatewayRuntime`，以及约 6,700 行无入口命令/CLI 会话浏览代码裁剪。未迁移到 CPA/sub2api，也没有宣称所有继承依赖已清理。最新验证状态见 [开发与验证状态](DEVELOPMENT_STATUS.md)。
